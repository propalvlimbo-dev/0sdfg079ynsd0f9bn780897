# Elytrix — lagfix v1

Пакет закрывает то, что видно в профиле spark, и не трогает ничего лишнего.
Все изменения делаются с бэкапами вида `*.bak-lagfix-<дата>`, повторный запуск
безопасен.

## Что чинит

| Причина из профиля | Что делает пакет |
|---|---|
| BLib падает в `Version.<clinit>` на 1.21.11 | добавляет `-Dblib.server.version=1.21.10` (штатный обход самой библиотеки); вместе с BLib начинают работать BCases, BMenu, VirtualEntityApi |
| 19 young-GC за ~50 с, средняя пауза 41 мс, каждые ~2.6 с, аллокация 250 МБ/с | `GC_MODE=zgc` по умолчанию — паузы < 1 мс вместо 41 мс. Откат: `GC_MODE=g1` |
| CPU (system) 42–55%, I/O-стопы | `sync-chunk-writes=false` в `server.properties` (рекомендация Paper) |
| 35.5% медленных тиков в обфусцированных `oII.mloTI/mloOO` | имя плагина ищет `lagdoctor.sh` (по всем jar, включая вложенные библиотеки) |
| `[STDOUT] [OlI] [websocket] disconnected (code=1002)` и поток `WebSocketConnectReadThread-11981182` | `lagdoctor.sh` ищет клиент Java-WebSocket: переподключение в цикле = новый поток и буферы на каждую попытку (11.9 млн за аптайм), отсюда 250 МБ/с аллокации и всплески MSPT |

Не трогает: дистанции, энтити-активацию, автосейв (они уже настроены),
плагины, миры, ресурспак.

## Установка

```bash
curl -fsSL -o /tmp/lagfix.zip https://raw.githubusercontent.com/propalvlimbo-dev/0sdfg079ynsd0f9bn780897/<SHA>/elytrix-lagfix-v1.zip
unzip -oq /tmp/lagfix.zip -d /tmp/lagfix
bash /tmp/lagfix/install.sh /root/RW_GRIEF
```

Опции:

```bash
DISTANCE_TUNING=1 bash install.sh /root/RW_GRIEF   # view-distance<=8, simulation-distance<=6
NO_ZGC=1 bash install.sh /root/RW_GRIEF            # не трогать сборщик мусора
```

## После установки

1. Перезапустить сервер **целиком** — флаг `-Dblib.server.version` применяется только при старте JVM.
   `/plugman reload BLib` его не подхватит: в логе снова будет `UnsupportedVersionException`.
2. В логе проверить: `Server version 1.21.10 is set via property blib.server.version`
   и отсутствие `ExceptionInInitializerError` у BLib.
3. Запустить `bash lagdoctor.sh` из каталога сервера и прислать `lag-report.txt`.

## Как понять, что стало лучше

До: MSPT медиана 15.5, p95 29.6, max 155–448 мс, GC-паузы 41 мс каждые 2.6 с.
После ZGC в `logs/gc.log` не должно быть `Pause Young` с десятками миллисекунд,
а в spark `flat` — уйти строки `SafepointSynchronize::block` и
`G1CollectedHeap::attempt_allocation_slow`.

Остаток — это работа плагинов в главном потоке (50% времени медленных тиков).
Её убирает только правка конкретного плагина, который находит `lagdoctor.sh`.

## Окно наблюдения 30 минут (spark30.sh)

Ссылка spark за 30 минут показывает среднюю картину: один всплеск на 0.6 с
растворяется в 30 минутах нормальной работы. Поэтому данные собираются в двух
видах, и оба — текстовые, в логе:

```
/spark tickmonitor --threshold-tick 100
/spark profiler start --timeout 1800 --only-ticks-over 100
```

Первый печатает в консоль и `latest.log` каждую строку `Tick #N lasted 214.6 ms`
и `Tick #N included GC lasting 41.2 ms` — с отметкой времени. Второй пишет
профиль только по медленным тикам, поэтому всплески не размываются.

Оба работают одновременно: у spark несколько обработчиков тика
(`TickHook.addCallback`), конфликта нет.

Когда окно закончилось:

```
bash spark30.sh /root/RW_GRIEF report 30
```

Разбор считает по минутам: сколько было переподключений websocket, сколько
медленных тиков и пауз GC, и сравнивает минуты «со штормом» и «без». Если
медленные тики сосредоточены в минутах со штормом — это доказательство со
стороны сервера.

Снимок «прямо сейчас» (10 секунд, без spark):

```
bash spark30.sh /root/RW_GRIEF
```

Смотрит в `/proc/<pid>/status`: переключения контекста в секунду, число потоков,
и рост TIME_WAIT-сокетов. Шторм переподключений виден по >20000
переключений/сек и растущим десятками TIME_WAIT.

## JFR без перезапуска (jfr30.sh)

`-XX:StartFlightRecording` в `start.sh` для поиска лага не подходит по двум
причинам:

* `-XX:+FlightRecorder` — пустышка: с JDK 13 объявлен deprecated и ничего не
  включает, JFR давно бесплатен. JVM на него только печатает предупреждение.
* запись начинается на старте JVM. `duration=200s` — это первые 200 секунд,
  то есть загрузка мира и плагинов, когда игроков ещё нет. Лаг в игре в это
  окно не попадёт.

Правильно — включать запись на уже работающем сервере через `jcmd`, без
рестарта, ровно тогда, когда люди онлайн:

```
bash jfr30.sh /root/RW_GRIEF start 1800    # писать 30 минут
bash jfr30.sh /root/RW_GRIEF stop          # или остановить раньше
bash jfr30.sh /root/RW_GRIEF report        # разобрать flight.jfr в текст
```

Запись (`settings=profile`) стоит 1–2% CPU. Файл за 30 минут — десятки или
сотни МБ, после разбора его можно удалить.

Что смотреть в отчёте:

* **кто создаёт потоки** — событие `jdk.ThreadStart` несёт стек создания,
  поэтому JFR называет класс, который плодит потоки. Для обфусцированного
  плагина это тоже работает: будет видно `oII.xxx` или
  `org.java_websocket.client.WebSocketClient.run`. Проверено на тестовой JVM:
  654 потока, у 653 в стеке `Churn.main(String[]) line: 10`;
* **самые долгие паузы GC** с точным временем — если TPS просел в 12:34:45,
  видно, была ли там пауза;
* **safepoint** — сколько всего и самая долгая остановка мира;
* **горячие методы** и **аллокация по классам**;
* **кто с кем говорит по сети** — адреса, с которыми держит соединения
  сервер; удобно, чтобы опознать плагин по домену.

Если всё-таки нужен флаг в `start.sh`, рабочая форма такая (с `delay`, чтобы
не тратить окно на загрузку):

```
-XX:StartFlightRecording=settings=profile,delay=10m,duration=30m,filename=/root/RW_GRIEF/flight.jfr
```

### Ловим конкретный лаг

Одна запись на 7 минут может не попасть во всплеск: он эпизодический. Поэтому
запись включаем на несколько часов, а когда лагнёт — делаем снимок и смотрим
окно вокруг отметки времени:

```
bash jfr30.sh /root/RW_GRIEF start 14400      # 4 часа, файл пишется в конце
bash jfr30.sh /root/RW_GRIEF dump             # снимок без остановки -> part.jfr
bash jfr30.sh /root/RW_GRIEF window 15:45:26 10 /root/RW_GRIEF/part.jfr
```

`window` берёт **событийные** типы (остановки на блокировках, park, сокеты,
файлы, GC) — они пишутся все, не по сэмплам, поэтому в 20-секундном окне
видно каждое событие длиннее 15 мс с точным временем и стеком. Отметку
времени удобно брать из строки spark `Tick #N lasted ... ms`.

Сэмплы выполнения (`hot-methods`) в JFR разрежены: JVM снимает фиксированное
число сэмплов в секунду на все потоки, поэтому по ним видно только общую
картину. Для «что делал серверный поток в эти 600 мс» нужен spark с
`--only-ticks-over`, а JFR — для точных событий по времени.

### Разбор на глубину: кто читает файлы и кто аллоцирует

```
bash jfr30.sh /root/RW_GRIEF deep
```

Три таблицы по уже снятому `flight.jfr`:

* **какие файлы читаются** — путь, сколько раз, сколько кБ и суммарное время,
  и в каком потоке. Если 10 раз в секунду читается `world/region/*.mca` — это
  chunk I/O; если `playerdata/*.dat` — постоянные загрузки игроков; если
  конфиг плагина — плагин перечитывает его на каждое событие;
* **кто аллоцирует** — полный стек до первых шести кадров, так что видно
  не только `Pair.of` или `BigInteger.add`, но и класс-вызыватель (в тесте:
  `int[] <- BigInteger.add(...) <- FileChurn.main`);
* **кто паркуется** — стеки ожиданий с суммарными миллисекундами.

### Автоматический снимок в момент лага

Держать запись и вручную ловить момент неудобно. `watch` слушает лог и сам
делает `JFR.dump`, как только spark сообщает о медленном тике:

```
bash jfr30.sh /root/RW_GRIEF start 14400
nohup bash jfr30.sh /root/RW_GRIEF watch 150 > /root/RW_GRIEF/watch.log 2>&1 &
```

Нужен включённый `/spark tickmonitor --threshold-tick 150` — он и печатает
строки `Tick #N lasted 214.6 ms`. На каждый такой тик появится
`lag-YYYYmmdd-HHMMSS.jfr` и строка в `lag-events.log`.

Разбор:

```
bash jfr30.sh /root/RW_GRIEF window 12:34:56 10 /root/RW_GRIEF/lag-20261031-125942.jfr
```

Не держи одновременно `/spark profiler` и JFR: в общем профиле половина
«аллокаций сервера» оказывается внутренней статистикой spark
(`RollingAverage.add(BigDecimal)`), а блокирующее чтение консоли
(`Server console handler` в `FileInputStream.read0`) выглядит как нагрузка,
хотя это поток, который просто ждёт ввода.

### Частая выборка и интервалы между лагами

Обычный JFR сэмплит редко (1–2 сэмпла на 400-мс всплеск), поэтому в окне не
видно, чем был занят `Server thread`. Режим `HI=1` поднимает частоту выборки
до 2 мс (правится копия `profile.jfc`, лежащая рядом с java сервера):

```
HI=1 bash jfr30.sh /root/RW_GRIEF start 900
bash jfr30.sh /root/RW_GRIEF window 16:13:49 10 /root/RW_GRIEF/lag-20261031-161349.jfr
```

В конце вывода `window` теперь есть секция «чем был занят Server thread в
окне» — стек верхних кадров. `HI=1` держать долго не надо: 10–15 минут
хватает на несколько всплесков, файл растёт быстро.

Интервалы между всплесками:

```
bash jfr30.sh /root/RW_GRIEF ticks 40
```

Печатает время, длительность и дельту до предыдущего. Если дельта ровная
(50–60 секунд) — это задача по расписанию, а не нагрузка.

### Разобрать все снимки сразу

Имена файлов и время вручную вводить не нужно:

```
bash jfr30.sh /root/RW_GRIEF windows
```

Скрипт сам обходит `lag-*.jfr`, берёт время из имени файла, считает окно
±10 секунд и печатает по каждому всплеску: события в окне и «чем был занят
Server thread». Если по всем файлам выводится «сэмплов нет» — запись шла с
обычной частотой, нужен запуск с `HI=1`.

## Проверка «а не голодает ли JVM по CPU» (cpu / cpu-report)

Симптом, который это ловит: тик занимает 470–570 мс, а внутри JVM — ни паузы
GC, ни блокировки, ни работы в стеке. Значит поток просто не получал CPU:
квота контейнера, шумный сосед на гипервизоре или ZGC, съевший ядра.

```
cat /sys/fs/cgroup/cpu.max ; nproc ; cat /proc/loadavg
nohup bash jfr30.sh /root/RW_GRIEF cpu 1800 > /root/RW_GRIEF/cpu.out 2>&1 &
# ... ждём лагов ...
bash jfr30.sh /root/RW_GRIEF cpu-report
```

`cpu` раз в секунду пишет `cpu.log`: `nr_throttled`, время троттлинга,
израсходованный CPU, PSI (`/proc/pressure/cpu`), loadavg и долю CPU процесса.
`cpu-report` считает эпизоды троттлинга и сверяет их с `lag-events.log`
(время берётся из `watch`): «лаг 16:19:38 — троттлинг +0.4 с» или «троттлинга
нет». Это ответ, а не догадка.

## Кто ест память и процессор (procs)

```
bash jfr30.sh /root/RW_GRIEF procs
```

Печатает: ядра и квоту CPU, `free -m`, `/proc/swaps`, топ-12 процессов по RSS,
все java-процессы с RSS и временем жизни, число потоков в системе.
Если java-процессов больше одного — второй держит память в swap и может
даже писать в тот же мир: это первая вещь, которую надо исключить.

## find_pid: какой java-процесс смотреть

Если на машине больше одного java (например, старый сервер не был убит при
перезапуске), все замеры легко уходят не в тот процесс. Теперь `find_pid`
выбирает java, у которого `/proc/<pid>/cwd` совпадает с каталогом сервера,
а если такого нет — процесс с наибольшим RSS. `procs` печатает для каждого
java его каталог, время жизни, RSS и порты, а `start` показывает каталог
выбранного процесса — видно сразу, тот ли это JVM.

## После каждого перезапуска сервера

`/spark tickmonitor` живёт только внутри процесса: после restart его надо
включить снова, иначе `lag-events.log` перестаёт пополняться и `watch`
нечего ловить. Порядок:

```
/spark tickmonitor --threshold-tick 150
bash jfr30.sh /root/RW_GRIEF start 14400
nohup bash jfr30.sh /root/RW_GRIEF watch 150 > /root/RW_GRIEF/watch.log 2>&1 &
nohup bash jfr30.sh /root/RW_GRIEF cpu 3600 > /dev/null 2>&1 &
```

## Как читать вердикт cpu-report

`cpu-report` ставит метку на каждый лаг из `lag-events.log`:

* `МЕМОРИЯ` — в эти секунды читался swap (больше 5 страниц/с) или было
  больше 50 крупных page fault в секунду;
* `CPU` — JVM в эти секунды занимала 85% и больше от всех ядер машины;
* `ТРОТТЛ` — рос счётчик квоты CPU контейнера;
* `ни память, ни CPU` — значит тик ждал не ресурс, а код на главном потоке.

Отдельно печатается распределение CPU (медиана, p90, p99, пик) и сколько
секунд JVM держала 85%+ всех ядер — на 3-ядерной машине пик 296% означает,
что ядер не остаётся никому.

## hunt: форензика по снятому дампу

Когда `watch` уже поймал лаг, разбирать надо ОДИН файл — тот, где был самый
долгий тик:

```
bash jfr30.sh /root/RW_GRIEF hunt /root/RW_GRIEF/lag-20261031-181427.jfr
```

Четыре таблицы по этому файлу:

* окно записи и количество событий;
* **топ методов Server thread** — проценты считаются от сэмплов именно этого
  потока, а не от всех 43; native-сэмплы помечены `[native]`;
* **блокировки, ожидание GC и блокирующий ввод-вывод** — `JavaMonitorEnter`,
  `SocketRead`, `FileRead`, `FileWrite`, `ZAllocationStall` с миллисекундами;
* **GC и ZGC-сталлы** — сколько и самые долгие с точным временем.

Дампы весят 130–160 МБ каждый, после разбора их надо удалять:
`rm -f /root/RW_GRIEF/lag-*.jfr`.

## freeze: доказать или опровергнуть «замерло на секунду»

```
bash jfr30.sh /root/RW_GRIEF freeze /root/RW_GRIEF/lag-20261031-181427.jfr 500
```

JFR сэмплит только те потоки, которые **выполняются**. Поэтому если в
очереди сэмплов появляется дыра, это значит: в этот момент не работал НИ ОДИН
поток JVM — ни серверный, ни Netty, ни GC. Так выглядит либо stop-the-world
(долгая пауза GC), либо остановка всей виртуальной машины гипервизором.

`freeze` раскладывает все сэмплы по 100-мс корзинам и печатает провалы
длиннее порога, с указанием, что делал поток до и после. Затем печатает все
паузы GC, safepoint и ZGC-сталлы длиннее 50 мс — чтобы сверить по времени:
если провал совпал с паузой GC, причина найдена.

## steal: процессор, который забрал гипервизор

В `cpu.log` добавлены два столбца из `/proc/stat`: `steal` (процент ядер,
отобранных хостом) и `iow` (ожидание диска). Это единственный способ увидеть
снаружи, что VDS «замерзает» не по своей вине. `cpu-report` ставит метку
`STEAL` на лаг, если в эти секунды steal был 20% и выше.

Если `steal` высокий — флаги, GC и плагины не помогут: нужно писать
провайдеру про соседей на гипервизоре либо переезжать.

## blame: кто съел конкретный тик

```
bash jfr30.sh /root/RW_GRIEF blame /root/RW_GRIEF/lag-20261031-181427.jfr 18:14:27 5
```

Берёт окно +-N секунд вокруг отметки и печатает по сэмплам **только
серверного потока**: топ стеков и отдельно — кадры из плагинов/библиотек
(всё, что не `net.minecraft`, `java`, `io.netty`, `com.mojang`,
`ca.spottedleaf`, `org.bukkit` и т.п.). Второй блок и есть ответ на вопрос
«какой плагин съел тик» — с полным стеком вызова.

Плотность сэмплов тоже печатается: при 13-14 сэмплах в секунду на окно
в 10 секунд приходится ~130 сэмплов, этого хватает, чтобы назвать виновника.

## Сессия «под нагрузкой»: одна команда

```
bash jfr30.sh /root/RW_GRIEF session 90
```

Делает всё сразу:

1. останавливает старые `watch` и удаляет старые дампы (это важно: несколько
   `watch` одновременно снимали гигабайты и сами создавали лаги);
2. запускает JFR с частой выборкой 2 мс и `maxage=3m` — на диске всегда только
   последние 3 минуты, поэтому снимок весит единицы мегабайт, а не 130;
3. поднимает один `watch` с паузой 30 с между снимками;
4. запускает `cpu` (CPU, память, swap, steal).

Дальше только `/spark tickmonitor --threshold-tick 150` в консоли сервера и
обычная игра.

Когда лагнуло:

```
bash jfr30.sh /root/RW_GRIEF catch
```

`catch` берёт последний дамп, время из его имени и сам запускает `blame` —
печатает топ стеков серверного потока и отдельно кадры из плагинов.
Проверить, что всё пишется: `bash jfr30.sh /root/RW_GRIEF status`.

## top: виновник по самому тяжёлому лагу

```
bash jfr30.sh /root/RW_GRIEF top 3
```

Берёт `lag-events.log`, убирает дубли, сортирует по длительности, показывает
топ и для каждого лага сам находит подходящий снимок (сделанный после тика и
не позже 3 минут — это `maxage`), после чего печатает стеки серверного потока
и кадры из плагинов. Одна команда — три худших лага с разбором.

## now: снять и разобрать прямо сейчас

Строки в `lag-events.log` может не быть (tickmonitor выключен, тик ниже порога,
перезапуск сервера). Тогда разбор не ждёт лага:

```
bash jfr30.sh /root/RW_GRIEF now 120
```

Снимает текущую запись (`JFR.dump`, без остановки), берёт последнюю минуту-две,
печатает стеки серверного потока, кадры из плагинов и события GC >= 50 мс.
Пока сервер лагает — это отвечает на вопрос сразу.

Ограничение: в записи хранятся только последние 3 минуты (`maxage=3m`), так
что `now` показывает недавнее прошлое, а не весь час.

## tasks: кто заваливает планировщик задачами

```
bash jfr30.sh /root/RW_GRIEF now 120      # снять текущее
bash jfr30.sh /root/RW_GRIEF tasks       # кто создаёт задачи
```

Ищет в сэмплах аллокаций объекты `CraftTask`, `CraftScheduler`,
`ServerSchedulerReportingWrapper`, `BukkitTask` и по стеку создания называет
источник: первый кадр вне серверного/Bukkit-кода — это вызывающий плагин.
Верхушка серверного потока в `CraftScheduler$1.compare` и
`PriorityQueue.siftDownUsingComparator` означает, что очередь задач выросла до
тысяч элементов и её разбор идёт каждый тик.

## psend: кто слушает исходящие пакеты

```
bash jfr30.sh /root/RW_GRIEF psend
```

Сканирует `plugins/*.jar` (весь каталог, ~3 с на 150 МБ) и печатает jar-ы, у
которых есть метод `onPacketSending` — то есть синхронный слушатель
`PacketSendEvent`. Именно из-за такого слушателя ProtocolLib перекидывает
каждый исходящий пакет, отправленный не из главного потока, в главный через
`BukkitScheduler.runTask` (`NettyChannelInjector.processOutbound`, строка
`if (hasMainThreadListener(packetType) && !Bukkit.isPrimaryThread())`).
Каждое такое перекидывание — новый `CraftTask` в приоритетной очереди
планировщика; когда их десятки тысяч, главный поток тонет в
`CraftScheduler$1.compare` / `PriorityQueue.siftDownUsingComparator`.

`tasks` показывает объём аллокаций по источникам (MB, доля, MB/мин) и сам
подсказывает протоколовский случай.

### Если после рестарта `now` пишет «файл не создан»

Запись JFR живёт внутри JVM и умирает вместе с ней при перезапуске сервера.
С v22 `now` это понимает: если снимать нечего, он сам запускает запись, ждёт
указанное число секунд и разбирает её. Одна команда, без подготовки.

Чтобы дальше снимок был мгновенным, один раз после старта сервера:

```
HI=1 MAXAGE=3m MAXSIZE=300m bash jfr30.sh /root/RW_GRIEF start 7200
```

Тогда запись идёт два часа по кругу (в файле всегда последние 3 минуты), а
`now 120` просто достаёт их и разбирает за пару секунд.

## spikes: где именно всплески (для «фриз на 1 секунду»)

```
bash jfr30.sh /root/RW_GRIEF spikes 10            # по now.jfr
bash jfr30.sh /root/RW_GRIEF spikes 10 файл.jfr
```

Раскидывает сэмплы `Server thread` по секундам и показывает самые горячие:
сколько сэмплов в секунду, медиану по окну и листовые кадры этой секунды.
Секунда, где сэмплов втрое больше медианы, помечается `<<< ВСПЛЕСК` — это и
есть «лаг на одну секунду», и рядом видно код, который в ней работал.

10 сэмплов при выборке 10 мс = ~100 мс работы в этой секунде; 100 сэмплов =
~1 с, то есть тик целиком.

## waits: кто ЖДАЛ (для «тик занял 2 секунды, а CPU не рос»)

```
bash jfr30.sh /root/RW_GRIEF waits 50
bash jfr30.sh /root/RW_GRIEF waits 200 файл.jfr
```

Достаёт из JFR `jdk.FileWrite / FileRead / FileForce / SocketRead / SocketWrite /
ThreadPark / JavaMonitorEnter / JavaMonitorWait` длиннее порога и печатает
длительность, поток, путь и стек. Это ответ на случай, когда `spikes` не видит
всплеска: поток не работал, а ждал диск, сокет (MySQL/сеть) или лок. Выборка
`jdk.ExecutionSample` такие тики не показывает — она ловит только RUNNABLE.

## tune.sh: пакет оптимизаций ядра

```
bash tune.sh /root/RW_GRIEF
```

Меняет только те ключи, что реально есть в конфигах (остальные пропускает с
пометкой), делает `.bak` на каждый файл, идемпотентен:

* `server.properties`: `sync-chunk-writes=false`, `simulation-distance=6`
* `config/paper-world-defaults.yml`: `chunks.max-auto-save-chunks-per-tick: 8`
* `bukkit.yml`: `ticks-per.autosave: 12000`
* `spigot.yml` (`world-settings.default`): радиус активации ИИ (animals 16,
  monsters 24, misc/water 8, villagers 16), `merge-radius` (item 3.5, exp 4.0),
  `max-entity-collisions: 2`, `tick-inactive-villagers: false`,
  `item-despawn-rate: 4000`

## once: одна команда, которая сама пишет и сама находит провал

```
bash jfr30.sh /root/RW_GRIEF once 20
```

Пишет 20 минут (выборка 2 мс, в файле всегда последние 15 минут), потом сам
разбирает и печатает четыре блока:

1. **провалы главного потока** — секунды, в которых серверный поток почти не
   работал, хотя перед этим работал. Это и есть «моргнуло на секунду».
   Рядом печатается, что поток делал за секунду до и после провала.
2. **где поток ждал** дольше 100 мс — диск, сокет, лок, парковка. Если здесь
   пусто, а провал есть, значит время ушло не на ожидание.
3. **паузы GC и сафпоинты** дольше 50 мс.
4. **топ стека** главного потока за всю запись — кто съел процессор.

Если запись уже идёт, `once` её просто использует и ничего не перезапускает.
Запускать при онлайне, когда лагает — он ловит именно то окно.

## memlog / memreport: дешёвый сторож памяти

Фризы «волнами» часто приходят не из кода, а из ядра: когда кончается RAM,
оно вытесняет страницы в своп, и весь мир на это время встаёт. В JFR это
выглядит как пустота, а не как всплеск.

```
bash jfr30.sh /root/RW_GRIEF memlog 120     # сторож на 2 часа, ~0% CPU
bash jfr30.sh /root/RW_GRIEF memreport      # вердикт по логу
pkill -f 'jfr30[.]sh .* memloop'            # остановить раньше
```

Пишет в `mem.log` строку раз в 5 с: свободная RAM, занятый своп, RSS сервера,
PSI memory/io, страницы swap-in/out в секунду, major faults в секунду, load.
`memreport` считает максимумы и печатает вердикт: если PSI memory >= 10%,
swap-in >= 20 стр/с или major faults >= 50/с — память в дефиците.

## memsplit: куда ушла память сервера

```
bash jfr30.sh /root/RW_GRIEF memsplit
```

Печатает по одному процессу: RSS, число потоков, занятый/использованный heap,
metaspace + code cache, оценку стеков и **разницу** между RSS и кучей. Если
эта разница больше полутора гигабайт — виновата не куча, а нативные буферы
(Netty direct, до `-Xmx` по умолчанию), арены malloc или JIT. Рядом —
`free -m` и шесть самых толстых java-процессов на машине.

## memfix.sh: потолок нативной памяти

```
bash memfix.sh /root/RW_GRIEF            # direct 1024 МБ, metaspace 768 МБ
bash memfix.sh /root/RW_GRIEF 1536 1024  # если в логе появится direct OOM
```

Замер: RSS сервера 11 740 МБ при `-Xmx7168M` — то есть **4.5 ГБ живут вне
кучи**. Netty (ProtocolLib + packetevents + packetevents внутри античита) по
умолчанию может занять direct-буферов до `-Xmx`, а metaspace не ограничен
вовсе. Скрипт вставляет две строки в FLAGS вашего `start.sh`, проверяет
синтаксис и оставляет `.bak`. Ожидаемый RSS после рестарта ≈ heap + direct +
metaspace + 300 МБ.

## mspt: из чего складывается тик

```
bash jfr30.sh /root/RW_GRIEF mspt 5          # 5 минут записи
bash jfr30.sh /root/RW_GRIEF mspt now.jfr    # разобрать готовый файл
```

Пишет 5 минут с выборкой 2 мс и печатает:

* **оценку MSPT** — сколько миллисекунд на тик уходит в среднем;
* **распределение длительности тика** — сколько тиков было <5, 5-10, 10-20,
  20-30, 30-50 и >50 мс, плюс худший тик. Тики восстанавливаются по кластерам
  сэмплов: разрыв больше 12 мс = граница тика;
* **подсистемы** — блочные сущности, мобы, чанки, планировщик, сеть, редстоун,
  жидкости, взрывы, генерация — с долей и прямым вкладом в мс/тик;
* **плагины** — какой плагин сколько мс/тик отнимает на главном потоке;
* **топ листовых кадров** — конкретные методы, а не «ванильный код»;
* **паузы GC и сафпоинты** дольше 20 мс и их суммарная доля времени.

Мс/тик считается как `сэмплы × 2 мс / (окно / 50 мс)`, поэтому цифры
складываются: сумма по подсистемам равна оценке MSPT.
